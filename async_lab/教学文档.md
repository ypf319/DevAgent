## 1. 第一层：为什么需要异步？—— "等待"是问题的根源

### 1.1 问题

假设你要调用 3 次一个需要 1 秒的接口。最直观的写法是：

```python
import time

for i in range(1, 4):
    time.sleep(1)      # 等 1 秒
    print(f"完成 {i}")
```

总耗时大约 3 秒。这就是**同步（阻塞）**：每一步都必须等上一步结束。

### 1.2 对应的脚本：`step1_sync_vs_async.py` 的第 1 部分

实测输出：

```text
1) 同步 time.sleep   ：3.02s
```

**关键洞察：** `time.sleep(1)` 不只是让"这一行代码"等待，而是**把整个线程冻住了**。在这 1 秒里，CPU 空闲，程序什么别的事也干不了。

### 1.3 你应该记住的

> **阻塞 = 等待时整个线程被占住。**
> 对于 I/O 密集的程序（大量时间花在等网络上），这是巨大的浪费。

到这里为止，我们还没有引入任何新概念。接下来的每一层都只是在解决"如何在等待时去干别的事"。

## 2. 第二层：协程、`await` 与事件循环（最小心智模型）

### 2.1 三个新名词

| 名词 | 最简单的理解 |
|---|---|
| **协程（coroutine）** | 用 `async def` 定义的函数。调用它**不会执行**，只会返回一个"待执行的任务单" |
| **`await`** | "我要等这件事，等的时候你（事件循环）去跑别人" |
| **事件循环（event loop）** | 一个单线程的"调度员"，在多个协程之间来回切换 |

### 2.2 一个必须先理解的现象：调用 `async def` 不会执行

```python
async def fetch(item_id, delay=1.0):
    await asyncio.sleep(delay)
    return {...}

coro = fetch(1)     # 这一行什么都没执行！只得到一个协程对象
print(coro)         # <coroutine object fetch at 0x...>
```

只有被**等待（await）**或者被**交给事件循环**，它才真正运行。这是新手最容易踩的第一个坑（见第 10 节）。

### 2.3 `await` 到底做了什么？

`step1` 中的异步串行写法：

```python
async def run_async_serial():
    results = []
    for i in range(1, N + 1):
        results.append(await fetch(i, DELAY))   # 每次 await 都会等到结束才继续
    return results
```

实测：

```text
2) 异步串行 await    ：3.00s   <-- 反直觉：没有变快
```

**这是本项目最重要的反直觉结果，请停下来想一想：**

- 代码里确实用了 `async/await`
- 但是 `await fetch(1)` 会等 `fetch(1)` **完全结束**才执行下一行
- 所以 `await` 只是"语法上允许让出"，**它本身不产生并发**
- 串行 `await` 的总耗时 = 任务数 × 单次耗时 = 3 × 1s = 3s

> **`async/await` 是"能并发"的前提，不是"已经并发"。**

### 2.4 那么 `await` 在什么时候才会"让出"？

只有当被等待的对象**真正需要挂起等待**（比如 `asyncio.sleep`、网络读写）时，事件循环才有机会去跑别的协程。如果一个协程里全是普通的计算、没有任何 `await` 点，它会一直霸占事件循环直到结束。第 8 节会用这一点解释 CPU 密集任务为什么帮不上忙。

### 2.5 程序入口：`asyncio.run`

```python
if __name__ == "__main__":
    asyncio.run(main())
```

`asyncio.run` 做三件事：创建事件循环 → 运行 `main()` 直到结束 → 关闭事件循环。**你不应该在一个已经运行的协程里再调用 `asyncio.run`**。

## 3. 第三层：`gather` —— 真正的并发从这里开始

### 3.1 问题

同样的 3 个任务，怎么让它们的等待时间**重叠**？

### 3.2 解法：`asyncio.gather`

```python
async def run_async_gather():
    results = await asyncio.gather(*(fetch(i, DELAY) for i in range(1, N + 1)))
    return results
```

`gather` 做的事情是：**同时把 3 个协程交给事件循环**。第一个协程遇到 `sleep` 挂起时，事件循环去跑第二个，第二个挂起后去跑第三个。三个 1 秒的等待就"重叠"在了一起。

实测：

```text
3) 异步并发 gather   ：1.00s   <-- 这才变快
```

### 3.3 用时间线画出来

```text
串行：  [fetch1 ████████][fetch2 ████████][fetch3 ████████]          总 3s
并发：  [fetch1 ████████]
        [fetch2 ████████]                                          总 1s
        [fetch3 ████████]
```

### 3.4 `gather` 的两个特性

1. **结果顺序与传入顺序一致**（不是完成的先后顺序）。`results[0]` 永远对应第 1 个协程。
2. **它会等待所有协程结束**。如果你想"谁先完成先处理"，要用 `as_completed`（本项目没有涉及，见第 10 节）。

### 3.5 本层小结

> **异步的价值 = 把等待时间重叠。**
> 要实现重叠，必须用 `gather`（或 `Task`，下一层）把协程同时交给事件循环。

到这里，你已经能解释 README 里那句核心话了：**`async/await` 只是前提，`gather` 才是真的并发。**

## 4. 第四层：`Task` —— 什么时候开始跑？

### 4.1 问题

`gather` 是"一次性全交出去并等待结果"。如果我想**先启动任务，然后自己继续干别的事，稍后再取结果**，怎么办？

### 4.2 解法：`asyncio.create_task`

```python
tasks = [asyncio.create_task(fetch(i, 1.0), name=f"task-{i}") for i in range(1, 4)]
```

`create_task` 会把协程**登记**为一个任务，然后**立刻返回**。它不会阻塞当前协程。

### 4.3 `step2_tasks.py` 实测输出，逐行解读

```text
[0.00s] 创建 3 个任务（create_task）
[0.00s] create_task 立刻返回，主协程继续执行，没有被阻塞
[0.00s] 此刻任务状态 done：[False, False, False]
[0.00s] sleep(0) 让出后，任务状态 done：[False, False, False]
[0.50s] 0.5s 后，任务名：['task-1', 'task-2', 'task-3']
[0.50s] 0.5s 后，任务状态 done：[False, False, False]
[1.00s] 全部完成，结果 id：[1, 2, 3]
[1.00s] 最终任务状态 done：[True, True, True]
```

请注意两个容易被忽略的细节：

**细节 1：`done() == False` 不等于"没在跑"。**
`sleep(0)` 之后任务**已经开始执行了**，只是还没完成（它们卡在 `sleep(1.0)` 那里）。`done()` 只回答"完成了没有"，不回答"开始了没有"。

**细节 2：为什么要 `await asyncio.sleep(0)`？**
`create_task` 之后，任务要等主协程**让出控制权**才有机会运行。`sleep(0)` 是一个"什么都不等、只让出一次"的技巧。你在下一层会看到，它正是"让事件循环转一圈"的标准写法。

### 4.4 `Task` 与 `gather` 怎么选？

| 场景 | 推荐 |
|---|---|
| 一次性启动一批任务，全部等完再继续 | `gather` |
| 先启动，中途做别的事，之后再取结果 | `create_task` + 之后 `await` |
| 需要给任务命名、单独取消某一个 | `create_task` |

### 4.5 一个新手必看的坑：保存 Task 的引用

事件循环只持有任务的**弱引用**。如果你 `create_task` 后不保存返回值，任务可能在完成之前就被垃圾回收。正确做法是用变量或集合保存（本脚本的 `tasks` 列表就是这么做的）。

## 5. 第五层：超时、取消与清理

### 5.1 问题

网络请求可能卡很久。我想"最多等 2 秒，超时就放弃"，并且**放弃时要关掉连接、释放资源**。

### 5.2 先理解取消是什么

`step3_timeout_cancel.py` 的核心被取消协程：

```python
async def slow_job(name: str, delay: float):
    log(f"{name} 开始")
    try:
        await asyncio.sleep(delay)
        log(f"{name} 正常结束")
    except asyncio.CancelledError:
        log(f"{name} 收到取消信号")
        raise                       # 必须重新抛出，见下文
    finally:
        log(f"{name} 执行清理（finally）")
```

**关键认识：取消不是"立刻杀死"，而是"在下一个 `await` 点，往协程里扔一个 `CancelledError` 异常"。**

所以：
- 协程必须有 `await` 点，取消才能生效（否则它一直运行，没人能打断它）
- `finally` 无论正常结束、超时还是取消都会执行——**这是释放资源的标准位置**
- `except CancelledError` 里处理完后**应该 `raise`**，让取消信号继续向上传播

### 5.3 `wait_for`：自动超时

```python
try:
    await asyncio.wait_for(slow_job("任务A", delay=5), timeout=2)
except TimeoutError:
    log("外层捕获到 TimeoutError（任务A 已被自动取消）")
```

实测：

```text
--- 1. wait_for 超时 ---
[0.00s] 任务A 开始
[2.00s] 任务A 收到取消信号
[2.00s] 任务A 执行清理（finally）
[2.00s] 外层捕获到 TimeoutError（任务A 已被自动取消）
```

注意时间线：任务本来要 5 秒，但 2 秒时 `wait_for` 自动调用了取消，任务在 2 秒处收到 `CancelledError`，执行 `finally`，然后外层才拿到 `TimeoutError`。**超时 = 自动取消 + 抛异常。**

### 5.4 手动取消：`task.cancel()`

```python
task = asyncio.create_task(slow_job("任务B", delay=5))
await asyncio.sleep(1)
task.cancel()
try:
    await task
except asyncio.CancelledError:
    log("await 被取消的任务，抛出 CancelledError")
```

实测：

```text
--- 2. 手动 cancel ---
[2.00s] 任务B 开始
[3.00s] 主协程调用 task.cancel()
[3.00s] 任务B 收到取消信号
[3.00s] 任务B 执行清理（finally）
[3.00s] await 被取消的任务，抛出 CancelledError
```

注意：`task.cancel()` 和"收到取消信号"在同一时刻（3.00s）。这是因为 `cancel()` 只是**登记请求**，任务真正被唤醒并处理取消，发生在主协程下一次让出控制权的时候。

> 这里的时间戳显示的是**相对于模块加载时的累计时间**（`START` 是全局变量）。这一点在第 6 节会再次遇到，别被数字误导。

### 5.5 本层小结

- 长任务必须能被取消，取消靠 `await` 点生效
- 资源释放放在 `finally`
- `except CancelledError` 处理完要 `raise`
- 超时用 `wait_for`，手动取消用 `task.cancel()`

## 6. 第六层：异步生成器 —— "边算边出"（流式输出）

### 6.1 问题

前面的例子都是"全部完成再一起返回"。但 LLM 生成文字是**一个字一个字吐出来的**。如果我要"拿到一条就立刻处理一条"，怎么办？

### 6.2 异步生成器：`async def` + `yield`

```python
async def stream_results(n: int, delay: float = 1.0):
    for i in range(1, n + 1):
        data = await fetch(i, delay)
        yield data              # 每完成一个就交出去
```

消费它要用 `async for`：

```python
async for item in stream_results(3):
    log(f"收到 {item['id']}")
```

把它和普通生成器对照：

| | 普通生成器 | 异步生成器 |
|---|---|---|
| 定义 | `def` + `yield` | `async def` + `yield` |
| 消费 | `for x in gen()` | `async for x in gen()` |
| 中间可以 `await` 吗 | 不可以 | 可以 |

### 6.3 `step4_async_gen.py` 实测输出

```text
--- 1. 流式（async for）：完成一个就打印一个 ---
[1.00s] 收到 1
[2.00s] 收到 2
[3.00s] 收到 3

--- 2. 批量（gather）：全部完成才一起返回 ---
[4.01s] 一次性收到 [1, 2, 3]
```

**注意：第二段显示 4.01s，而不是 1s。** 这是因为日志时间戳是从模块加载开始累计的：流式部分先花了 3 秒，批量部分又花了 1 秒，合计约 4 秒。这个"看起来不对"的数字，恰好提醒你：**读时间戳要看它的起点是什么**。

### 6.4 流式 vs 批量：怎么选？

| 目标 | 选择 | 理由 |
|---|---|---|
| 尽早拿到第一份结果（打字机效果、进度条） | 流式 | 第一条 1 秒就到手 |
| 必须全部结果齐全才能继续 | 批量 `gather` | 总耗时最短，逻辑最简单 |

> 两者不冲突：你可以用 `gather` 并发地跑一批任务，再用 `as_completed` 或异步生成器逐个消费完成的结果。

### 6.5 与 AI Agent 的关系

LLM 的 SSE 流式输出，在客户端的代码形态就是 `async for chunk in stream:`。这一节的写法，就是你以后读 Agent 框架源码时会频繁看到的模式。

## 7. 第七层：`Queue` 与背压 —— 生产者和消费者

### 7.1 问题

前面的例子中，任务数量是我们事先确定的。但真实系统里，**数据是持续产生的**（比如不断有用户请求、不断有文档要处理）。生产速度和消费速度往往不一致，怎么办？

### 7.2 解法：`asyncio.Queue`

```python
queue = asyncio.Queue(maxsize=2)    # 队列最多存 2 个
```

- 生产者：`await queue.put(item)`
- 消费者：`item = await queue.get()`

### 7.3 背压（backpressure）：这是本层的核心

`maxsize=2` 的意思是：**队列满了，`put` 会自动等待**。

```text
生产者 → [队列 ■■] → 消费者
          满了
生产者 ← 被迫等待（自动降速）
```

这就是**背压**：下游处理不过来，就反过来让上游慢下来。如果没有背压，生产者会不停地塞数据，内存无限增长，最终撑爆。

### 7.4 `step5_queue_pipeline.py` 实测输出，关键行解读

```text
[0.00s] 生产者放入 1（队列大小 1）
[0.10s] 生产者放入 2（队列大小 1）
[0.20s] 生产者放入 3（队列大小 1）
[0.30s] 生产者放入 4（队列大小 2）
[0.70s] 消费者1 处理完 1（长度 7）
[0.70s] 生产者放入 5（队列大小 2）
[0.80s] 消费者2 处理完 2（长度 7）
[0.80s] 生产者放入 6（队列大小 2）
[1.40s] 消费者1 处理完 3（长度 7）
[1.51s] 消费者2 处理完 4（长度 7）
[1.51s] 生产者结束
[2.11s] 消费者1 处理完 5（长度 7）
[2.11s] 消费者1 收到结束标记，退出
[2.21s] 消费者2 处理完 6（长度 7）
[2.21s] 消费者2 收到结束标记，退出
```

逐段看：

- **0.00–0.30s**：生产者很快放入 1–4。消费者还在处理第一批，队列被填满到 2。
- **0.30s 之后**：生产者想放入 5，但队列满了，所以要等到 0.70s 消费者1 取走一个才放入。**这段等待就是背压在起作用。** 你会注意到 "放入 5" 的时间点被"推迟"到了 0.70s。
- **1.51s 之后**：生产者已经结束，但队列里还有 5、6 没处理完，消费者继续慢慢消化。

> 注意 `queue.qsize()` 的值在日志里只会是 1 或 2，从不超过 `maxsize=2`。这就是你能"亲眼看见"的上限。

### 7.5 结束标记：`None`

消费者 `await queue.get()` 会一直等下去。要让它退出，常用做法是生产者最后放入一个特殊值（这里是 `None`）作为"哨兵"。有几个消费者就要放几个哨兵。

```python
for _ in range(CONSUMER_COUNT):
    await queue.put(None)
```

### 7.6 `task_done` 与 `join`

- 每取出一个任务处理完，调用 `queue.task_done()`
- `await queue.join()` 会阻塞，直到所有放入的条目都被标记为完成

这个脚本里 `join` 基本是"保险"，因为 `gather` 已经等到了所有消费者退出。它在更复杂的场景（生产者和消费者不在同一个 `gather` 里）才真正关键。

### 7.7 本层小结

| 概念 | 一句话 |
|---|---|
| `Queue(maxsize=N)` | 协程之间安全的数据通道 |
| 背压 | 队列满了 `put` 自动等待 |
| `None` 哨兵 | 通知消费者"没有更多数据了" |

## 8. 第八层：异步的边界 —— 什么时候它帮不上忙？

### 8.1 问题

前面所有的"加速"，都是因为任务在**等待**。如果任务是**纯计算**（比如算一个大循环），异步还能加速吗？

### 8.2 先看单次 CPU 计算的基线

```python
def cpu_work(n: int) -> int:
    total = 0
    for i in range(n):
        total += i * i
    return total
```

实测（单次）：

```text
3) 单次 CPU 计算     ：0.36s
```

3 个任务串行的理论值约 1.08s。下面看各种方式的实测。

### 8.3 `step6_threads_vs_async.py` 完整实测

```text
I/O 任务：3 个，每个 1.0s

1) 线程池做 I/O      ：1.01s
2) 协程做 I/O        ：1.00s

CPU 任务：3 个，每个约 5000000 次循环
3) 单次 CPU 计算     ：0.36s
4) 协程直接做 CPU    ：0.98s
5) to_thread 做 CPU  ：0.98s
6) 线程池做 CPU      ：0.98s
7) 进程池做 CPU      ：0.60s
```

### 8.4 逐条解读

**I/O 部分（1、2）：线程池和协程都快。**
两者都能让等待重叠，所以都约 1 秒。

**CPU 部分（4、5、6）：三者都约 0.98s，等于串行。**

- **4) 协程直接做 CPU**：`cpu_work` 里没有 `await`，协程一旦开始就霸占事件循环，直到算完才让出。所以 `gather` 变成了"一个接一个跑"，还会卡住别的协程。
- **5) `to_thread` 做 CPU**：把计算丢到线程里，看起来像是"并行"了，但 CPython 的 **GIL（全局解释器锁）** 保证同一时刻只有一个线程在执行 Python 字节码，所以纯 CPU 计算仍然是串行的。
- **6) 线程池做 CPU**：同理，受 GIL 限制，没有提速。

**进程池（7）：0.60s，真正快了。**
每个进程有自己独立的解释器和 GIL，所以可以真正并行。0.60s 比 0.98s 快，但没有达到理想的 0.36s，因为进程启动和数据传递有开销。**具体加速比取决于你机器的核心数**（你的机器核心数不同，结果会不同）。

### 8.5 一张表记住它

| 任务类型 | 推荐工具 | 原因 |
|---|---|---|
| I/O 密集（网络、文件、数据库、LLM） | `asyncio` 或线程池 | 等待可以重叠 |
| CPU 密集（大计算、图像处理、大规模解析） | 进程池 | 只有多进程能真并行 |
| 在协程里必须调用阻塞的同步库 | `asyncio.to_thread` | 避免卡住事件循环 |

> **记住核心句：协程只解决"等待"，不解决"计算"。**

### 8.6 为什么 README 说"不要在协程里调用 `time.sleep` / `requests.get`"？

因为它们会**阻塞整个事件循环**。它们不是 `await` 点，所以事件循环没法切换到别的协程。这就是 step1 里 `time.sleep` 那一组的问题在异步场景下的放大版。

## 9. 第九层：回到 AI Agent —— 并发调用 LLM

### 9.1 前面学的东西在 Agent 里对应什么？

| 本项目 | 在 AI Agent 里的对应场景 |
|---|---|
| `fetch`（I/O 等待） | 调用 LLM API、检索向量库、调用外部工具 |
| `gather` | 并行检索多个来源、同时问多个模型、批量评测 |
| 异步生成器 `async for` | LLM 流式输出（SSE、打字机效果） |
| `Queue` + 背压 | 任务队列、限流（不要一下子把 API 打爆） |
| `wait_for` 超时 | 给 LLM 调用设置超时，防止一直挂住 |
| `finally` 清理 | 关闭 HTTP 连接、保存中间状态 |

### 9.2 `step7_llm_concurrent.py` 的核心代码

这一节是你学完前面所有内容后，会**一眼看懂**的代码：

```python
async def ask(client: httpx.AsyncClient, prompt: str, index: int) -> dict:
    start = time.perf_counter()
    response = await client.post(
        settings.llm_base_url,
        headers={"Authorization": f"Bearer {settings.llm_api_key}"},
        json={"model": settings.llm_model,
              "messages": [{"role": "user", "content": prompt}],
              "max_tokens": 100},
        timeout=60,
    )
    response.raise_for_status()
    elapsed = time.perf_counter() - start
    content = response.json()["choices"][0]["message"]["content"]
    return {"index": index, "elapsed": elapsed, "content": content}

async def main():
    async with httpx.AsyncClient() as client:
        results = await asyncio.gather(
            *(ask(client, prompt, i) for i, prompt in enumerate(PROMPTS, start=1))
        )
```

逐点对应你已经学过的：

- `await client.post(...)`：网络 I/O，就是 `fetch` 的真实版本
- `async with httpx.AsyncClient()`：异步上下文管理器，保证退出时关闭连接（第 5 节的 `finally` 思想）
- `gather(...)`：三个问题同时发出，总耗时 ≈ 最慢的那个

## 10. 常见坑速查

| # | 坑 | 现象 | 解决 |
|---|---|---|---|
| 1 | 写了 `async def` 但没 `await` | 报 `coroutine ... was never awaited`，逻辑根本没执行 | 调用协程时用 `await` 或交给 `gather` / `create_task` |
| 2 | 在协程里调用阻塞函数 | 其他协程全部"卡住"，并发失效 | 换成异步版本，或用 `asyncio.to_thread` |
| 3 | `create_task` 后不保存引用 | 任务可能被回收，静默丢失 | 用变量或集合持有 |
| 4 | 以为 `async` 能加速 CPU 计算 | 没变快（见第 8 节） | CPU 密集用进程池 |
| 5 | 混淆 `gather` 和 `as_completed` | 以为顺序是完成顺序，结果对不上 | `gather` 按传入顺序返回；`as_completed` 谁先完成先给你 |
| 6 | 忘记处理取消 | 超时后资源没释放 | 清理逻辑放 `finally`，`except CancelledError` 里 `raise` |
| 7 | 误以为 `await` 就是并发 | 写了 async 还是慢（见 2.3） | 并发靠 `gather` / `create_task` |
